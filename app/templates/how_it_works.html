DEFENSIVE ARCHITECTURE

How XShield Works

An explainable, multi-stage detection and correlation pipeline that evaluates user input, assesses risk, derives behavioral patterns, and groups security events into actionable incidents.

01

Application Input

User-controlled text submitted via the browser form or received via the versioned integration API (POST /api/v1/events). Server-side length bounding and character format validation are applied immediately.

SecurityEventContract
02A

Rule Detector (Heuristics)

Six explainable rule categories (R001–R006). Preprocesses input with case-folding and single-layer entity/URL decoding. Identifies markup, execution functions, event handlers, and obfuscation. Never executes payload.

app.detector.rules
02B

ML Predictor (TF-IDF + LR)

Transforms raw text into 54,919 character n-gram features (3–5 characters) using a saved offline-trained vectorizer. A balanced Logistic Regression classifier predicts binary label and calibrated XSS probability.

app.ml.predictor
03

Hybrid Fusion Signal

Fuses normalized rule score (0.0–1.0) with ML XSS probability using configurable weights (default: 50% rule + 50% ML). Tracks detector agreement (both benign, both attack, or disagreement) for transparent telemetry.

app.detector.hybrid_detector
04

Risk Engine & Response Action

Maps the continuous hybrid signal to a 0–100 risk score and project-defined severity tiers: Low (0–29), Medium (30–59), High (60–79), Critical (80–100). The Action Engine applies defensive decisions: allow, flag, block, or block_and_alert.

app.risk & app.response
05

Behavioral Intelligence (Phase 6)

Evaluates bounded recent security events per application. Tracks repeated suspicious activity, normalized endpoint targeting, burst frequency (short-window velocity), and detection pattern diversity to quantify ongoing attack behavior.

app.services.behavior
06

Incident Correlation (Phase 7)

Dynamically clusters related events within configured time windows based on shared request IDs, identical normalized endpoints, or overlapping matched-rule signatures. Computes deterministic incident hashes without manual rule scripting.

app.services.incidents
07

XShield Security Intelligence Console

All completed events, derived incidents, behavioral summaries, and application metadata are persisted securely in SQLite using parameterized queries and visualized in real time in the XShield Security Console.

SOC Console (/dashboard)

Detailed Pipeline Specifications

Why Character-Level TF-IDF?

Traditional word-level tokenizers fail on obfuscated XSS payloads because attackers split keywords (e.g. <scr<script>ipt>) or use URL/entity encodings. Character n-grams (3 to 5 characters) capture sub-word punctuation, tag openers, and delimiters directly.

Why Heuristic Rules alongside ML?

Machine learning provides generalization across unseen attack variants but can be prone to dataset bias. Explainable rules guarantee immediate detection of deterministic signatures (e.g. javascript: schemes and onerror= attributes) with exact violation reasons.

Fail-Closed Security Design

If any detector, vectorizer, or risk engine fails, XShield defaults to fail-closed application policy: access is denied and a controlled internal security event is logged rather than allowing potentially malicious input to bypass unanalysed.
